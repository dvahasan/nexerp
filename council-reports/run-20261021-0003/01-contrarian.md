# 01 — Contrarian report: NexERP

## Verdict
Assume this system is live on Railway today: it fails first through its own back doors, not through load. A hardcoded developer master key, an auto-seeded `admin/admin` owner account, and a mass-assignment path to cross-tenant takeover mean a mildly curious outsider owns every company's data before any inventory race condition matters. Underneath that, the stock ledger — the product's one source of truth — can silently drift from reality through hard deletes, direct qty edits and location bookkeeping gaps, and nobody would know because there is no test, no health check, no alerting, and no backup story. The public API, the flagship integration feature, appears to have never been run end-to-end: it cannot authenticate against its own schema and would fail validation if it did.

## Findings

### F1. Developer "god mode" API guarded by a hardcoded fallback key — Critical
Evidence: `backend/routes/developer.js:9-17` (`process.env.DEV_MASTER_KEY || "nexdev2026"`), `backend/routes/developer.js:156-233` (generic CRUD on every model), `backend/routes/developer.js:237-253` (cross-company action logs), `backend/server.js:90` (`/api/dev` excluded from action logging).
`/api/dev/db/query/:model`, `POST/PUT/DELETE /api/dev/db/:model/:id` and `/api/dev/settings` give full read/write/delete over all 23 models **across all tenants** — Users (password hashes), Companies (API keys), Transactions, Ledger — authenticated only by a static header whose fallback value is committed to the repo. If `DEV_MASTER_KEY` is unset on Railway, anyone who reads the code (or guesses "nexdev2026") owns the entire database; updates run with `runValidators: false` (developer.js:210) so even schema invariants don't hold. These routes are deliberately excluded from the ActionLog middleware, so the most dangerous operations in the system are the only unlogged ones. The frontend stores the key in `localStorage` (`frontend/src/pages/DeveloperDashboard.jsx:18`), so it also leaks to any XSS.
Action: Remove the fallback default and refuse to mount `/api/dev` when `DEV_MASTER_KEY` is unset; replace the universal CRUD explorer with specific, logged, read-mostly endpoints; require a real authenticated enterprise/dev user, not a shared static header.

### F2. Production boot seeds a well-known owner account every start — Critical
Evidence: `backend/server.js:163` (`connectDB(seedData)`), `backend/seedData.js:20-49` (company `NEX-01`, owner `admin`/password `admin`, users `ahmed/sara/khaled` with password `123`), `backend/routes/auth.js:80-104` (no rate limiting or lockout on login).
The deployed server recreates company `NEX-01` with owner credentials `NEX-01 / admin / admin` on every cold start if missing — in the same production database as real tenants. The owner role carries every permission including user and company management. Combined with zero login throttling, even the "123" passwords on the other seed users are trivially brute-forced. Anyone on the internet can log into the production system as an owner right now, generate API keys, and create traffic/cost.
Action: Gate `seedData()` behind `NODE_ENV !== 'production'` or an explicit `SEED_DEMO=true` flag; use strong random seed passwords printed once; add rate limiting (e.g. express-rate-limit) on `/api/auth/*`.

### F3. Cross-tenant takeover chain via mass assignment in user update — Critical
Evidence: `backend/routes/users.js:127-141` (`$set rest` with unfiltered body), `backend/routes/auth.js:87-92` (enterprise login by `username + isEnterprise`), `backend/routes/enterprise.js:73-85` (`/assume/:companyId` checks only `ownedCompanies`), `backend/middleware/auth.js:39-41` (enterprise company assumption from token), `backend/routes/company.js:11-16` (PUT /api/company writes raw `req.body`).
`PUT /api/users/:id` only strips `role`/`permissions` (and only for non-`canManagePermissions` callers) and then `$set`s the remaining body verbatim. A manager — or any admin of *their own* company — can set `isEnterprise: true` and `ownedCompanies: [<any other company's ObjectId>]` on a non-owner user, log that user in via enterprise login (no company code needed), then call `/api/enterprise/assume/<victimCompanyId>` to mint a valid JWT for a company they never belonged to; `resolvePerms` then grants them their role's powers inside the victim tenant (a manager gets `canManageUsers` → can reset victim users' passwords). Similarly `PUT /api/company` passes `req.body` straight to `findByIdAndUpdate`, letting any `canManageCompany` user set arbitrary fields including `apiKeys` and `active`. Multi-tenant isolation — the product's core security promise — is defeated by its own user-management endpoint.
Action: Whitelist updatable fields on both endpoints (`name, nameEn, email, phone, password, preferredLanguage, active` for users); never accept `isEnterprise`, `ownedCompanies`, `companyId`, `apiKeys` from request bodies.

### F4. Secret hygiene: fallback JWT secret, live credentials on disk, passwords logged in plaintext — High
Evidence: `backend/middleware/auth.js:4` (`JWT_SECRET || "nexinv_secret"`), `backend/.env` lines 1–7 (MONGODB_URI with embedded DB username+password `mongodb://…[masked]`, JWT_SECRET `…[masked]`, CLOUDINARY_API_KEY/SECRET `…[masked]`), `backend/routes/auth.js:19` (`console.log("Register payload:", req.body)`).
If `JWT_SECRET` is ever missing in an environment, every token is forgeable with the committed string "nexinv_secret" — and the actual secret in `.env` is a short human-readable phrase, not a random key. `backend/.env` holds live Atlas connection credentials and the Cloudinary API secret in the working tree (gitignored and untracked — good — but it is the production DB from a developer laptop, with no apparent rotation). Worst: the register route logs the full request body, **including the plaintext password**, to stdout, which Railway retains in its log store.
Action: Delete the `console.log` at auth.js:19 immediately; make the app refuse to boot without `JWT_SECRET`/`DEV_MASTER_KEY`; rotate the Atlas and Cloudinary credentials (they've lived unrotated on a dev machine); use separate dev/prod databases.

### F5. Login and /me responses over-share: password hash, company API keys, to every role — High
Evidence: `backend/routes/auth.js:92` and `auth.js:104` (`res.json({ token, user, company, … })` with full Mongoose docs; contrast `auth.js:112-113` where `/me` deletes `passwordHash`), `backend/models/User.js` (no `toJSON` transform), `backend/models/Company.js:23,36-42` (`googleMapsApiKey`, `apiKeys`), `backend/server.js:74` (CORS reflects any origin with `credentials: true`).
Login returns the raw user document — including `passwordHash` — and the full company document — including `apiKeys` and `googleMapsApiKey` — to **every** role, down to `viewer`. A read-only viewer can lift the company's integration API keys and then write stock movements through `/api/public/checkout` (once that route works, see F6), bypassing all role permissions. The bcrypt hash exposure also hands offline cracking material to anyone with a stolen session. The allow-all CORS config means any website a logged-in user visits can call the API with their localStorage token if it is ever leaked via XSS.
Action: Add a `toJSON` transform on User stripping `passwordHash`; return a redacted company (mask API keys except on an owner-only settings endpoint); pin CORS to the real frontend origin(s).

### F6. Public checkout API is dead on arrival: schema mismatch, missing ownerId, racy idempotency, toy API keys — High
Evidence: `backend/routes/publicApi.js:20` (`Company.findOne({ apiKeys: apiKey })` matches whole array elements), `backend/models/Company.js:36-42` (apiKeys are `{key, name, createdAt}` subdocuments), `frontend/src/pages/Settings.jsx:568-571` (keys generated client-side as plain strings with `Math.random()`), `backend/routes/publicApi.js:103` (`req.company.ownerId` — no such field exists on Company), `backend/models/Transaction.js:14` (`userId … required: true`), `publicApi.js:48-53` (idempotency check is read-then-insert), `Transaction.js:46` (idempotencyKey index is **not unique**).
Three independent defects say this route was never exercised end-to-end: (1) the lookup queries `apiKeys` as if elements were strings while the schema defines subdocuments — depending on how the client-generated string keys survived casting through `PUT /api/company`, either storage or lookup fails; (2) `req.company.ownerId` is undefined, so `userId` is null and the required-field validation aborts every checkout; (3) even if fixed, two concurrent requests with the same `idempotencyKey` both pass the non-atomic existence check and double-decrement stock, because the index is not unique. The keys themselves are `Math.random()` strings minted in the browser — low entropy, plaintext in the DB, no scoping, no revocation audit.
Action: Integration-test the route; add a server-side key-generation endpoint using `crypto.randomBytes`, store hashed keys; make `(companyId, idempotencyKey)` a unique partial index and rely on the duplicate-key error; resolve the acting user explicitly.

### F7. Stock ledger integrity drifts silently: hard deletes, uncontrolled qty edits, location divergence — High
Evidence: `backend/routes/items.js:258-266` (hard `findOneAndDelete` of items), `backend/routes/items.js:213-255` (`PUT /items/:id` applies `{...req.body}` — including `qty` — with no Ledger entry), `backend/routes/transactions.js:170-176` (ItemStockLocation only updated when `warehouseId` supplied), `backend/routes/publicApi.js:87-93` (upsert `$inc: {qty: -qty}` can create a location row born negative), `backend/routes/transactions.js:281-286` (OUT-cancel re-adds stock with unchecked update result).
The Ledger (qtyBefore/qtyAfter chain) is only as trustworthy as the writers, and three writers bypass it: deleting an item orphans its Transactions, Ledger rows and ItemStockLocation rows (none are cleaned up or blocked); any `canEdit` user can set `qty` directly via item update with no audit trail; and transactions recorded without a warehouse never touch per-location rows, so `Item.qty` and the sum of `ItemStockLocation.qty` diverge permanently — the migration script `backend/migrate_ledger.js:36-43` even has to invent a `NONE` location to paper over this. Once warehouse totals disagree with item totals, every WMS/KPI screen built on them reports fiction, and there is no reconciliation job to detect it.
Action: Soft-delete items (the `deletedAt` field already exists and is honored by queries — items.js:19); route all qty changes through an ADJUST transaction; add a periodic reconciliation check (Item.qty vs. Σ locations vs. ledger replay) that raises an Alert on mismatch.

### F8. Unauthenticated write endpoints and unbounded logging create silent cost and abuse channels — Medium
Evidence: `backend/routes/developer.js:118-154` (`POST /api/dev/track-demo` — no auth, outbound call to `http://ip-api.com/json/…` per hit), `backend/routes/enterprise.js:96-106` (`POST /api/enterprise/create` — unauthenticated enterprise-admin creation, no input validation), `backend/server.js:87-134` (ActionLog writes full request body + IP + UA for every mutating request; extra `User.findOne` per login attempt), `backend/models/ActionLog.js` (no TTL index).
Anyone can script `/track-demo` to insert unlimited DemoVisit rows, each triggering a plain-HTTP geolocation call to a free rate-limited third party (an outbound dependency that fails silently and leaks visitor IPs over cleartext). `/enterprise/create` is a second, undocumented open-registration path that mints `role: "admin"` enterprise users. Meanwhile ActionLog grows without bound on Atlas, storing request bodies (only `password` is masked — `server.js:113-114` — not emails, phone numbers, or future secret-bearing fields) — storage cost and a PII liability that nobody is pruning.
Action: Delete or key-protect `/enterprise/create`; rate-limit and captcha-less-throttle `/track-demo` (or move counting client-side); add a TTL index (e.g. 90 days) on ActionLog and stop storing raw bodies.

### F9. Untrusted-input pipelines: SSRF via photo-from-url; CSV import skips permissions and trusts LLM output — Medium
Evidence: `backend/routes/items.js:271-298` (server-side `fetch(url)` of arbitrary user-supplied URL, response uploaded to Cloudinary and its URL returned), `backend/routes/import.js:16` (route guarded by `protect` only — no `need("canAdd")`), `backend/routes/import.js:42-49` (Gemini response `JSON.parse`d and used as the column map with no validation against `CORE_FIELDS`), `backend/routes/import.js:10` (multer memoryStorage, no file-size limit), `backend/routes/import.js:114` (`insertMany` with no dedupe).
`photo-from-url` is a classic read-SSRF: any `canAdd` user can make the Railway container fetch internal/metadata URLs and read the response back as a hosted file. The CSV import is callable by a **viewer** (role with `canAdd:false`), silently violating the permission model; the LLM's column map is parsed and applied unvalidated, so a response (or a prompt-injected CSV header) mapping a column to `companyId` or `qty` corrupts data without error; an unbounded multipart upload is buffered fully in memory (the 10mb JSON limit at server.js:75 does not apply to multipart), a one-request memory-DoS; and re-importing the same file duplicates every item.
Action: Enforce `need("canAdd")` on import; validate that mapped values ∈ `CORE_FIELDS`; add multer `limits.fileSize`; block private/metadata IP ranges (or remove photo-from-url); dedupe on sku/barcode like `items.js:159-171` does.

### F10. Operational blindness: server keeps serving with no database, no health endpoint, no backup/restore story — Medium
Evidence: `backend/config/db.js:14-20` (connection failure is caught, logged and swallowed; server still listens), `backend/server.js:166-168` (listen unconditionally), `backend/railway.json:7-9` (restart policy `ON_FAILURE` — never triggers because the process doesn't fail), no `/health` route in `backend/server.js:136-160`; `backend/migrate_ledger.js` and `backend/routes/admin.js:21-36` (migrations as ad-hoc scripts / a GET endpoint); no test suite or CI anywhere in the repo (confirmed by `backend/package.json:9-13`, scripts are start/dev/seed only).
If Atlas is unreachable at boot or drops later, the API stays up returning 500s on every request; Railway's restart policy can't help and nothing alerts anyone — the exact "silent failure" a warehouse discovers mid-shift. Domain errors like insufficient stock also surface as HTTP 500 (`backend/errors.js:110-123` defaults to 500 for plain `Error`s), making real outages indistinguishable from business rejections in any monitoring. There is no backup/restore procedure, no migration framework (schema changes are one-off scripts run by hand), and zero automated tests guarding the money path (transactions/ledger). **Assumption:** backups rely entirely on whatever the Atlas tier provides; nothing in the repo configures or documents them.
Action: Add `/health` that checks `mongoose.connection.readyState` and exit(1) on failed initial connect so Railway restarts; map domain errors to 4xx; document/verify Atlas backup + restore; add at least a transaction/ledger integration test before any further feature work.

## Assumptions and limits
- Read ≈30 files: effectively all of the backend security/data surface (server.js, middleware, 13 of 24 routes including all flagged ones, 6 of 23 models, config, seeds, migrate script, errors, broadcast, AlertService, Procfile/railway.json, package.json, .gitignore, both .env files — values not reproduced) plus targeted frontend files (api.js, Settings.jsx excerpt, DeveloperDashboard.jsx and Landing.jsx via grep). Roughly 70–80% of backend LOC examined, under 5% of frontend LOC; skipped node_modules, nex_dashboard, the PDF blueprint, codemod scripts, and most frontend pages per the brief.
- Not read: `backend/routes/barcode.js`, `stats.js`, `files.js`, `settings.js`, `warehouses.js`, `bins.js` and the remaining reference-data routes; `seed-*.js` beyond headers; most of `bom.js` (only the produce-commit section). Similar mass-assignment/permission patterns likely recur there (Assumption).
- Assumption: the backend is actually deployed on Railway against the Atlas cluster named in `backend/.env` (Procfile/railway.json and the brief say so; I could not verify the live environment or whether `DEV_MASTER_KEY`/`JWT_SECRET` are set there — the Critical grades of F1/F2 hold even if they are, because of the seeded credentials and repo-committed fallbacks).
- Assumption: the public repo visibility is unknown; F1's "anyone who reads the code" applies with certainty only to people with repo access, and to everyone if the repo is public.
- The F6 claim that checkout never worked is inferred from three mutually independent code defects; I did not run the server to confirm (project is read-only for this review).
