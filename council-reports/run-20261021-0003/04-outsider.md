# 04 — Outsider report: NexERP

## Verdict

A newcomer who trusts the README will be onboarded into an application that no longer exists: the docs describe a single-file, single-company v1.1, while the code is a 24-route, multi-company, multi-warehouse system with enterprise mode, AI chat, BOM/MRP and a developer dashboard — none of it documented. The clone-and-run path mostly works by luck (auto-seeding saves it), but the documented login steps fail, half the environment variables the code reads are undocumented, and missing ones silently fall back to hardcoded secrets. An evaluator browsing the repo sees codemod scripts inside `src/`, Python brace-checkers at the root, a directory literally named `{backend,frontend`, five competing seed scripts and zero tests — the overall impression is a capable prototype that one person understands, not a product a second person can safely touch yet.

## Findings

### F1. README documents a previous generation of the application — High
Evidence: `README.md:314-333` (§Project Structure) vs `backend/server.js:22-45` and `frontend/src/main.jsx:3`; `README.md:65-70` vs `backend/middleware/auth.js:8-13`; `README.md:260-308` (§API Reference) vs the 24 route mounts in `backend/server.js:137-160`.
The README claims "Single-file Express API (all routes, models, middleware)" and "App.jsx — entire React app, ~2200 lines"; in reality the backend has 24 route modules and 23 models, and the frontend entry is `TailwindApp.jsx` with 33 page files under `frontend/src/pages/`. The permissions table is wrong: README says Manager can Add/Edit items but not Manage Users; `auth.js:10` says the opposite (`canAdd:false, canEdit:false, canManageUsers:true`), and the documented `canTx` permission was split into `canTxIn`/`canTxOut` (`auth.js:22-26`). The API Reference omits roughly two-thirds of the surface (`/api/warehouses`, `bins`, `bom`, `ai`, `import`, `public`, `dev`, `enterprise`, `company`, `files`, `barcode`, `sources`, `destinations`, `projects`, `reasons`). Entire headline features — multi-company registration, enterprise accounts, WMS, BOM/MRP, CSV/AI import, demo mode, invoice printing, the public API — appear nowhere in the docs. A newcomer cannot distinguish what the system does from what it did a year ago; a customer evaluating against the README is evaluating the wrong product. README also says "inline styles (no CSS framework)" (`README.md:47`) while Tailwind 4 is installed (`frontend/package.json:28-33`).
Action: Rewrite the README against the current code (or auto-generate the API section from the route files), and state the real feature set; delete or clearly date the stale sections.

### F2. The documented first login fails: company code is required but never mentioned — Medium
Evidence: `README.md:396` ("login with `admin` / `admin`") vs `backend/routes/auth.js:80-104` (login requires `code`; without it the request takes the *enterprise* path and returns "Invalid enterprise credentials"), `backend/seedData.js:32` (actual credentials are `NEX-01 / admin / admin`), `frontend/src/pages/Login.jsx:156-165` (the form has a Company Code field).
A fresh clone that follows the Getting Started section verbatim hits a login form with an undocumented third field; entering only admin/admin fails with a confusing enterprise error. The only place the company code is revealed is a server console log. Registration (`/api/auth/register`, including the enterprise variant) is likewise completely undocumented. This is the very first interactive moment of an evaluation, and it fails.
Action: Update Getting Started to `NEX-01 / admin / admin`, and add a short section on company registration and enterprise login.

### F3. Env-var documentation covers roughly half of what the code reads — Medium
Evidence: `README.md:339-356` documents `MONGODB_URI`, `JWT_SECRET`, `CLOUDINARY_*`, `PORT`, `VITE_API_URL`. The code additionally reads `GEMINI_API_KEY` (`backend/routes/ai.js:53`, `backend/routes/import.js:33`), `SMTP_HOST/PORT/SECURE/USER/PASS/FROM` (`backend/mailer.js:16-27`), `CLIENT_URL` (`backend/mailer.js:137,160`), `DEV_MASTER_KEY` (`backend/routes/developer.js:10`), and accepts `MONGO_URL` as an alias (`backend/config/db.js:8`).
Notably, the author's own `backend/.env` contains the SMTP block but has no `GEMINI_API_KEY` or `DEV_MASTER_KEY` entries at all (keys verified by name only; values not read into this report) — so even the reference environment runs the AI features in fallback mode and the developer dashboard on its default key. A newcomer has no way to know these variables exist, what enables what, or which are optional.
Action: Add a complete env-var table (name, required/optional, what breaks without it) and ship `backend/.env.example` / `frontend/.env.example` files.

### F4. Missing env vars silently fall back to hardcoded, repo-visible secrets — High
Evidence: `backend/middleware/auth.js:4` (`process.env.JWT_SECRET || "nexinv_secret"`), `backend/routes/developer.js:10` (`process.env.DEV_MASTER_KEY || "nexdev2026"`).
Because the server boots happily without these variables (and even without a DB — `config/db.js:9-12` logs and continues), a newcomer or evaluator who misses a line in `.env` gets a fully working deployment whose JWTs are signed with a secret printed in the public source, and whose `/api/dev/*` endpoints (user counts, company list, DB stats, OS stats) open to anyone who sends the default `x-dev-key` header. Nothing warns at startup. From the outside, this reads as "the demo works" while actually being forgeable-token territory; it is exactly the trap docs exist to prevent.
Action: Fail fast (refuse to start) when `JWT_SECRET` is unset in production, remove the `DEV_MASTER_KEY` default, and document both.

### F5. "AI Assistant" silently degrades to canned keyword matching — Medium
Evidence: `backend/routes/ai.js:53-98` — with no `GEMINI_API_KEY` (or on any Gemini error) the endpoint falls through to a hardcoded if/else over keywords like "low", "value", "today" and returns formatted responses indistinguishable from the AI path.
For a prospective customer in a demo, the product appears to have a working AI advisor when it may be pattern-matching five phrases. The only disclosure is a hint buried in the catch-all response ("Connect a Gemini API key…", `ai.js:97`). Honest labelling matters to evaluator trust: if the fallback is discovered mid-evaluation, it taints everything else shown.
Action: Tag fallback responses visibly (e.g. a "basic mode" badge in `AiChat.jsx`) and document the feature's dependency on the key.

### F6. Repo hygiene undermines evaluator confidence: codemods in src/, Python checkers at root, a `{backend,frontend` directory — Medium
Evidence: root listing — `check_brace.py`, `check_paren.py`, `check_jsx_tags.py`, `test_cat.js`, and a stray directory `D:\Web\nexerp\{backend,frontend\src}` (an escaped brace-expansion that never ran); `frontend/src/fixAlign.cjs`, `fixHeaders.cjs`, `fixSettings.cjs`, `makeResponsive.cjs`, `moveDetailPanel.js`, `refactorWh.cjs`, `refactorWh2.cjs`, `frontend/src/pages/rewrite_rounded.js`/`.cjs`; `backend/server.local.err.log`, `server.local.out.log` (0 bytes); `nex_dashboard/` — an abandoned stock Vite scaffold with the template README; `backend/migrate_ledger.js` (untracked one-off migration). All of these are untracked (verified via `git ls-files`), so a fresh clone is cleaner than this working copy — but anyone reviewing this machine, a zip, or a screen-share sees one-shot regex rewriters sitting next to production pages.
These are the first files an outsider's eye lands on, and they say "the author edits this codebase with throwaway scripts and nothing is cleaned up." The brace-expansion directory in particular signals commands pasted between shells without checking results.
Action: Delete the stray directory, logs, and `nex_dashboard/`; move any codemod worth keeping to a `scripts/` folder (gitignored or documented); delete the rest.

### F7. No tests, no linting, no CI — a newcomer has no definition of "safe change" — Medium
Evidence: `backend/package.json:9-13` and `frontend/package.json:5-9` (no test or lint scripts anywhere); the only verification artifacts are ad-hoc scripts `backend/test-api.js`, `test.js`, `test-photo.js`, which `.gitignore:32-34` deliberately excludes from the repo ("Test / seed scripts (optional)"); no CI config exists in the repo root.
With 20k+ LOC of frontend, 1,600-line pages (`frontend/src/pages/ItemPage.jsx`), and stock-mutating transaction logic, the only way a new developer can validate a change is manual clicking in two languages. Gitignoring the one API test script means even that is lost to a cloner. Time-to-first-safe-change for a newcomer is realistically days of reverse-engineering, and every change to transaction/ledger code is a leap of faith.
Action: Un-ignore and commit `test-api.js` as a smoke test, add ESLint to both packages, and start a minimal test suite around transaction stock math before any other refactoring.

### F8. Five seed scripts with overlapping purposes; one is destructive and none but one is documented — Low
Evidence: `backend/seedData.js` (auto-run on boot, `server.js:163`), `backend/seed.js` ("wipe & rebuild", per `seedData.js:6`, wired to `npm run seed` in `backend/package.json:12`), `backend/seed-test-data.js` (the only one in the README, `README.md:400-424`), `backend/seed-transactions.js`, `backend/seedEnterprise.js`.
A newcomer told to "seed the data" has a one-in-five guess, and the wrong guess (`npm run seed`) wipes the database — the script's destructive nature is stated only in a comment inside a different file. The README's description of `seed-test-data.js` (10 items / 39 transactions table) at least matches the file, but the others live only in the author's head.
Action: Document all five (purpose, safety, order) in the README or consolidate them into one script with flags.

### F9. Licensing and provenance don't check out — Low
Evidence: `README.md:447-449` declares "License: MIT" but no `LICENSE` file exists anywhere in the repo (verified at root); the git remote is named `NexERP` → `github.com/dvahasan/nexerp`, while work happens on branch `b1` with an unexplained relationship to `main`.
For a customer or contributor doing basic due diligence, "MIT" without a license file is legally meaningless, and an undescribed working branch makes it unclear which code is the product. Small items, but they are exactly what an evaluator's checklist catches first.
Action: Add a LICENSE file (and copyright holder), and either merge `b1` or note the branch strategy in the README.

## Assumptions and limits

- Approx. share read: ~25 files read in full (README, root/backend/frontend package.json, server.js, config/db.js, config reference via grep, middleware/auth.js, routes/auth.js, routes/ai.js (partial), routes/developer.js (partial), seedData.js, api.js (partial), main.jsx, vite.config.js, Login.jsx (grep), .gitignore) plus directory listings and targeted greps — roughly 15–20% of the ~182 non-vendor files. Skipped: all large page components, models, WMS/BOM/import internals, the blueprint PDF, Postman collections, `nex_dashboard` contents beyond a listing.
- `.env` files were inspected for key names and host *type* only (localhost vs cloud, presence/absence of keys); no secret values were read into or reproduced in this report. For the record: `frontend/.env` points VITE_API_URL at localhost and `backend/.env` at a local MongoDB — so the checked-out config is a dev setup, which slightly softens F4's immediate risk but not its clone-time trap.
- Runnability judged statically (per council rules — nothing was installed or executed). Assumption: `npm run dev` from the root works as wired, since the script chain (`package.json:8-10` → workspace dev scripts) and the Vite proxy (`vite.config.js:8-16`) are consistent; untested.
- Assumption: time-to-first-safe-change estimate ("days") is a judgement from code size, page sizes and absence of tests, not a measured onboarding.
- The council brief stated `.log` files were "committed into backend/"; git shows them untracked and 0 bytes — I report what `git ls-files` shows.
